2. Spesifikasi Teknis Autentikasi JWT (JSON Web Token)

Sistem autentikasi CRM Disty Akademi mengadopsi Stateless Token Authentication menggunakan algoritma HMAC-SHA256 (HS256). Implementasi ini bersifat murni (*native PHP* di app/Support/Jwt.php) tanpa ketergantungan library eksternal, menjamin performa tinggi, waktu respons instan, dan kompatibilitas penuh antar platform.

Parameter Konfigurasi Token (File .env & config/jwt.php):
  • Algoritma Signature: HS256 (HMAC with SHA-256)
  • Kunci Rahasia (Secret): JWT_SECRET (Tersimpan aman di sisi server)
  • Masa Berlaku (TTL): JWT_EXPIRES_SECONDS=28800 (8 Jam sejak waktu diterbitkan)
  • Skema Header Request: Authorization: Bearer <token>

2.1. Struktur Anatomi Token

Setiap token terdiri dari tiga segmen yang dipisahkan oleh karakter titik (header.payload.signature):

// 1. HEADER (Algoritma dan Tipe Token)
{
  "alg": "HS256",
  "typ": "JWT"
}

// 2. PAYLOAD (Data Identitas Pengguna & Klaim Waktu)
{
  "sub": 1,                     // ID unik pengguna di database
  "name": "Budi Santoso",       // Nama lengkap akun
  "email": "sales@disty.id",    // Email pengguna
  "role": "sales",              // Peran otorisasi: 'admin' atau 'sales'
  "iat": 1731675600,            // Waktu dibuat (Issued At epoch timestamp)
  "exp": 1731704400             // Waktu kedaluwarsa (Expiration epoch timestamp)
}

// 3. SIGNATURE (Tanda Tangan Kriptografi Anti-Pemalsuan)
HMACSHA256(
  base64UrlEncode(header) + "." + base64UrlEncode(payload),
  JWT_SECRET
)

2.2. Mekanisme Keamanan & Validasi Token

  1. Integritas Data Terjamin: Jika pihak luar mencoba memodifikasi isi payload (misalnya mengubah role dari "sales" menjadi "admin"), tanda tangan digital otomatis tidak cocok. Server langsung menolak dengan status 401 Unauthorized.
  2. Proteksi Timing-Attack: Validasi tanda tangan menggunakan perbandingan waktu tetap (hash_equals), mencegah peretas mengidentifikasi kecocokan tanda tangan berdasarkan perbedaan milidetik respons server.
  3. Pencegahan Algoritma None: Sistem secara eksplisit menolak algoritma di luar HS256, menutup celah keamanan bypass signature.
  4. Status Akun Real-time: Selain memverifikasi keaslian token, middleware Autentikasi.php selalu mengonfirmasi status is_active pengguna di database. Pengguna yang dinonaktifkan seketika kehilangan akses.

3. Diagram Alur Kerja API (Business Workflows)

3.1. Alur 1: Autentikasi Pengguna & Penanganan Sesi

1
Klien Mengirimkan Kredensial (POST /api/login)
Frontend mengirimkan email dan password. Server memvalidasi kecocokan hash password bcrypt dan memastikan akun dalam kondisi is_active = true.
2
Server Menerbitkan JWT Token
Server membentuk payload (ID, nama, email, role), mencatat waktu terbit dan kedaluwarsa (8 jam), lalu menandatanganinya dengan JWT_SECRET. Respon mengembalikan token dan objek profil.
3
Penyimpanan di Storage Lokal (Frontend)
Vue SPA menyimpan token di localStorage.setItem('crm_jwt_token', token).
4
Pengiriman Header pada Setiap Permintaan Data
Setiap pemanggilan API menyertakan header Authorization: Bearer <token>. Middleware Autentikasi.php memvalidasi token sebelum melanjutkan ke Controller.

3.2. Alur 2: Siklus Hidup Prospek (Lead Funnel & Closing)

Diagram Alur Status Prospek (Lead Stages):
[Baru (New)] → [Dikontak (Contacted)] → [Aktif (Active)] → [Negosiasi (Negotiation)] → [Berhasil (Won)] / [Ditolak (Lost)] / [Tidak Aktif (Inactive)]
  • Akuisisi Awal: Prospek masuk via input manual (POST /api/leads) atau unggah berkas Excel masal (POST /api/leads/import). Status awal adalah new.
  • Klaim Penjualan: Tim sales mengklaim prospek tanpa pemilik (unassigned) lewat POST /api/leads/{id}/claim, menetapkan assigned_to ke ID sales terkait.
  • Aktivitas & Interaksi: Sales mencatat log interaksi (telepon, chat WA, meeting) lewat POST /api/leads/{id}/activities. Waktu kontak pertama (first_contacted_at) tercatat otomatis.
  • Pendaftaran & Negosiasi: Peserta didaftarkan ke jadwal sertifikasi (POST /api/registrations). Lead bergeser ke status negotiation.
  • Pembayaran & Closing: Bukti bayar diunggah (POST /api/payments). Setelah Admin memverifikasi valid (PATCH /api/payments/{id}/verify), status lead otomatis naik ke won, pelanggan resmi masuk katalog customer aktif, dan follow-up pending ditutup otomatis.

3.3. Alur 3: Instruksi Admin ke Sales & Notifikasi Pengingat (Reminders)

  • Admin mendeteksi lead yang belum di-follow up atau macet di dashboard.
  • Admin menembakkan POST /api/leads/{lead}/remind-sales disertai pesan instruksi khusus dan tingkat urgensi (normal / urgent).
  • Sales menerima notifikasi real-time pada badge lonceng navbar (didukung polling otomatis tiap 10 detik via GET /api/reminders).
  • Sales membuka pesan dan menandai telah selesai dikerjakan lewat PATCH /api/reminders/{id}/complete.

3.4. Alur 4: Perhitungan & Pencairan Komisi Sales

  • Begitu pembayaran peserta di-ACC Admin, komisi sales otomatis terhitung di sistem (tabel commissions) dengan status awal pending.
  • Admin mereview performa dan menyetujui komisi via PATCH /api/commissions/{id}/approve.
  • Sales dapat memperbarui rekening pencairan kapan saja lewat POST /api/user/bank-account. Komisi yang belum cair otomatis mengikuti nomor rekening terbaru.
  • Admin mentransfer dana dan menandai komisi telah lunas via PATCH /api/commissions/{id}/pay. Sistem merekam snapshot historis rekening tujuan transfer demi transparansi audit keuangan.

5. Standar Format JSON Response & Penanganan Error

5.1. Respon Berhasil (HTTP 200 / 201)

// Contoh respon sukses mengambil profil pengguna (GET /api/user)
{
  "success": true,
  "data": {
    "id": 1,
    "name": "Budi Santoso",
    "email": "sales@distyakademi.com",
    "role": "sales",
    "phone": "081234567890",
    "bank_name": "BCA",
    "bank_account_number": "1234567890",
    "bank_account_name": "Budi Santoso",
    "bank_info": "BCA - 1234567890 (a.n Budi Santoso)"
  }
}

5.2. Respon Error Validasi Input (HTTP 422 Unprocessable Content)

{
  "message": "Email atau password salah.",
  "errors": {
    "email": [
      "Email atau password salah."
    ]
  }
}

5.3. Respon Error Token / Autentikasi (HTTP 401 Unauthorized)

// Kasus 1: Token tidak dikirimkan di header
{
  "success": false,
  "message": "Silakan masuk terlebih dahulu (Token Bearer diperlukan)."
}

// Kasus 2: Masa berlaku token telah habis (> 8 jam)
{
  "success": false,
  "code": "TOKEN_KEDALUWARSA",
  "message": "Sesi Anda telah berakhir, silakan login kembali."
}

// Kasus 3: Token palsu atau tanda tangan diubah pihak ketiga
{
  "success": false,
  "code": "TOKEN_TIDAK_VALID",
  "message": "Token otentikasi tidak valid."
}

5.4. Respon Hak Akses Ditolak (HTTP 403 Forbidden)

{
  "message": "Akses ditolak. Fitur operasional ini hanya dapat diakses oleh Admin."
}

6. Panduan Integrasi Klien (Vue SPA, Mobile & Postman)

6.1. Implementasi Klien JavaScript / Fetch API

// 1. Eksekusi Login & Penyimpanan Token
async function loginUser(email, password) {
  const response = await fetch('/api/login', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json', 'Accept': 'application/json' },
    body: JSON.stringify({ email, password })
  });
  
  const data = await response.json();
  if (response.ok && data.token) {
    localStorage.setItem('crm_jwt_token', data.token);
    console.log('Login berhasil! Token tersimpan:', data.token);
  }
}

// 2. Mengakses Endpoint Terproteksi
async function fetchDashboard() {
  const token = localStorage.getItem('crm_jwt_token');
  
  const response = await fetch('/api/dashboard', {
    headers: {
      'Accept': 'application/json',
      'Authorization': `Bearer ${token}`
    }
  });

  if (response.status === 401) {
    // Sesi habis, bersihkan storage & arahkan ke login
    localStorage.removeItem('crm_jwt_token');
    window.location.href = '/login';
    return;
  }

  const dashboardData = await response.json();
  return dashboardData.data;
}

6.2. Konfigurasi di Postman / Insomnia

  1. Tembak POST /api/login dengan body JSON kredensial.
  2. Salin string token dari respon.
  3. Pada tab Authorization di Postman:
    • Pilih Type: Bearer Token
    • Paste token ke dalam field Token.
  4. Seluruh endpoint di bawah /api/... kini dapat dites secara langsung tanpa kendala autentikasi.
